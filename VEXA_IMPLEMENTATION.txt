# 🚀 VEXA

## **VEXA: Architecture-Aware Autonomous Multi-Agent Software Engineering System**

### One-line explanation

> **VEXA takes a natural-language software requirement or an existing repository, autonomously understands the problem, plans the solution, writes/modifies code, runs tests, diagnoses failures, repairs the implementation, and verifies the final software — while experimentally evaluating different multi-agent architectures.**

---

# 1. What does VEXA actually do?

Suppose you open VEXA and type:

> **"Build a FastAPI task management API with JWT authentication, PostgreSQL, CRUD operations, Docker support and unit tests."**

You don't manually create:

```text
main.py
models.py
routes.py
database.py
schemas.py
Dockerfile
tests/
requirements.txt
```

VEXA does it.

The high-level process is:

```text
                 USER PROMPT
                     │
                     ▼
             REQUIREMENT ANALYSIS
                     │
                     ▼
              PROJECT PLANNING
                     │
                     ▼
             ARCHITECTURE DESIGN
                     │
                     ▼
              CODE GENERATION
                     │
                     ▼
              TEST GENERATION
                     │
                     ▼
              TEST EXECUTION
                     │
              ┌──────┴──────┐
              │             │
             PASS          FAIL
              │             │
              ▼             ▼
         VERIFICATION    DEBUGGING
              │             │
              │             ▼
              │           PATCH
              │             │
              │             ▼
              │       TEST AGAIN
              │             │
              └──────┬──────┘
                     ▼
               CODE REVIEW
                     │
                     ▼
              FINAL VERIFICATION
                     │
                     ▼
              WORKING PROJECT
```

That's the **product**.

But VEXA has another purpose.

### Verification Agent

Finally asks:


It checks:

```text

✓ No obvious regression
✓ Patch matches requested behaviour
✓ Code quality acceptable
```

# 11. The autonomous loop

This is one of the most important parts of VEXA.

It should **not** stop at the first generated code.

Instead:

```text
              CODE
                ↓
              TEST
                ↓
        ┌──── PASS? ────┐
        │               │
       YES              NO
        │               │
        ▼               ▼
     REVIEW          DEBUGGER
                        │
                        ▼
                     PATCH
                        │
                        ▼
                       TEST
```

We impose a maximum:

```text
MAX_ITERATIONS = 5
```

to prevent infinite loops.

So VEXA can autonomously reason:

> "The implementation failed because the database session isn't being closed."

then:

> "I'll patch the dependency."

then:

> "Run the tests again."

then:

> "All tests pass."

# 17. Sandbox

This is essential.

Never allow an LLM to freely execute arbitrary commands on your development machine.

VEXA should create:

```text
workspace/
   task_001/
```

and execute code inside a Docker container.

Example:

```text
VEXA
 │
 └── Docker Sandbox
       │
       ├── repository
       ├── dependencies
       ├── tests
       └── execution
```

Allowed:

```text
read code

run tests
run build
run linter
```

Blocked:

```text
system-level modifications
credential access
arbitrary host filesystem access
dangerous commands
```

This directly supports the course's safety, guardrail and secure deployment objectives.

# 20. Architecture C — Event Driven

Instead of direct agent-to-agent calls:

```text
CODE_CHANGED
TEST_FAILED
DEBUG_REQUIRED
PATCH_CREATED
TEST_PASSED
VERIFICATION_REQUIRED
```

Agents subscribe to events.

Example:

```text
TEST_FAILED
     │
     ▼
Debugger wakes
     │
     ▼
DEBUG_REQUIRED
     │
     ▼
Coder wakes
     │
     ▼
CODE_CHANGED
     │
     ▼
Tester wakes
```

This gives us a genuinely different orchestration model.

# 47. What we should NOT do

There are several traps.

### ❌ Don't make 15 useless agents

Your guidelines explicitly prohibit trivial agent projects such as generic Research/Writer/Proposal/Travel agents. 

### ❌ Don't make it only a chatbot

It must actually modify/run/test software.

### ❌ Don't use RAG just for decoration

It needs to demonstrably help repository understanding.

### ❌ Don't fabricate experimental results

Every metric must come from actual runs.

### ❌ Don't only compare architectures theoretically

Run the same benchmark through them.

### ❌ Don't make one person responsible only for UI

The handout explicitly says team members must contribute across agents, tools, orchestrator and integrations, and be capable of explaining/modifying the system during evaluation. 

### ❌ Don't make it dependent on one huge prompt

The point is orchestration.
